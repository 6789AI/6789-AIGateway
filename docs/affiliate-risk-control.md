# 邀请关系风控查询

管理员可以在用户管理页面通过邀请码或推广链接查询邀请关系，用于排查批量注册、恶意刷取活动额度等风险行为。

## 使用方法

1. 进入管理后台的“用户管理”页面。
2. 点击“邀请关系查询”。
3. 输入用户 ID、邮箱、邀请码（例如 `46fD`），或包含 `aff` 参数的推广链接（例如 `https://www.6789api.top/sign-up?aff=46fD`）。
4. 点击“搜索”或按 Enter，查看邀请链接归属人和直接受邀用户。

查询结果以匹配到的用户为主体，保留并展示该用户自己的邀请码，同时展示其上级邀请人和直接受邀用户。上级邀请人被软删除时仍展示并标记“已删除”；如果记录中存在 `inviter_id`，但对应账号已经硬删除或无效，则保留显示该邀请人 ID 并提示记录已不存在。没有 `inviter_id` 时显示该用户不是通过邀请注册的。

结果包含软删除用户，直接受邀用户按用户 ID 倒序分页。查询不递归展示二级或更深层邀请关系。受邀用户总数根据实际的 `inviter_id` 关系计算，不依赖邀请奖励或累计邀请次数字段。

查询默认对 ID、规范化邮箱和邀请码执行精确匹配，不进行模糊搜索，也不支持按用户名查询。同一个输入如果只命中一个用户就直接返回；如果跨字段命中多个不同用户，则返回歧义提示。管理员可以通过以下前缀强制指定查询类型：

- `id:123`
- `email:owner@example.com`
- `aff:46fD`

## 数据与缓存

查询直接使用现有的 `users.id`、`users.email`、`users.aff_code` 和 `users.inviter_id` 索引，不需要数据库迁移或数据回填。

该功能不使用 Redis 或服务端内存缓存。每次搜索和翻页都会读取主数据库，以便及时反映新注册、账号状态变化和软删除操作。已经被管理员硬删除的用户及其邀请归属数据无法恢复或查询。

## 邀请人数与回算

邀请人数以 `users.inviter_id` 记录的直接邀请关系为准。新用户通过普通注册或 OAuth 注册成功后，邀请人的 `aff_count` 都会增加一次；该计数不受支付合规状态、邀请奖励开关或固定奖励额度是否为零影响。

Root 管理员可以进入“系统设置 → 计费与支付 → 额度与邀请 → 邀请”，使用“回算人数”精确重建全部 `aff_count`。回算包含软删除用户，排除自我邀请、无效邀请人和已经硬删除的关系。该操作只修改邀请人数，不修改用户普通额度、待转入奖励、累计奖励或已有返利记录。

```http
POST /api/option/affiliate/recalculate-invite-counts
Authorization: Bearer <root-access-token>
```

## 邀请奖励与充值返利

“额度与邀请”的“邀请”页签提供三个互相独立且默认开启的开关：邀请者注册奖励、受邀者注册奖励、充值与兑换返利。关闭开关会保留已经填写的额度或比例；对应数值为零时不会发放奖励，但邀请人数仍正常统计。

充值与兑换返利默认比例为 `10%`，允许设置 `0–100%` 且最多两位小数。返利基数是被邀请人最终实际到账的内部额度，计算结果向下截断；开关开启、比例大于零且到账额度为正时，最低返利一个内部额度单位。返利只发给直接邀请人，不计算二级或更深层级。

以下来源会按规则计算返利：在线充值成功、兑换码兑换成功，以及管理员在钱包“订单历史”中手动完成真实待支付订单并勾选“发放邀请返利”。管理员在用户管理中直接增加额度不返利，订阅购买也不纳入返利。补单选项不能绕过全局返利开关、比例或支付合规限制。

比例和开关变更只影响之后完成的充值或兑换，不回算历史收入。支付回调或兑换重试继续使用返利来源唯一索引保证幂等。

钱包中的“待转入奖励”对应 `aff_quota`：这是已经获得但尚未转入普通余额的奖励，并非等待管理员审核。执行转入后该值减少；“总收入”对应 `aff_history`，表示累计历史奖励，不会因转入而减少。

## 邀请码约束

用户首次取得邀请码时，系统会生成并保存邀请码。邀请码创建后不可由用户或管理员修改、替换或重新生成，因此已经发布的推广链接会持续指向同一归属人。

推广链接的域名不参与归属判断。服务端只解析链接中的 `aff` 参数，不访问链接指向的网站；实际查询仍以数据库中的邀请码为准。

## 管理员接口

```http
GET /api/user/aff/search?q=id%3A3&p=1&page_size=20
Authorization: Bearer <admin-access-token>
```

`q` 支持裸用户 ID、邮箱、邀请码、完整推广链接以及 `id:`、`email:`、`aff:` 前缀。`p` 是受邀用户页码，`page_size` 最大为 100。

查询成功时返回精简的用户信息，不包含密码、访问令牌、OAuth 标识、余额或其他无关敏感字段：

```json
{
  "success": true,
  "message": "",
  "data": {
    "aff_code": "46fD",
    "owner": {
      "id": 1,
      "username": "owner",
      "display_name": "Owner",
      "email": "owner@example.com",
      "status": 1,
      "created_at": 1700000000,
      "deleted_at": null,
      "inviter_id": 8
    },
    "inviter": {
      "id": 8,
      "username": "inviter",
      "display_name": "Inviter",
      "email": "inviter@example.com",
      "status": 1,
      "created_at": 1690000000,
      "deleted_at": null,
      "aff_code": "AB12"
    },
    "invitees": {
      "items": [],
      "total": 0,
      "page": 1,
      "page_size": 20
    }
  }
}
```

没有任何用户匹配时仍返回成功响应，其中 `owner` 和 `inviter` 为 `null`，`invitees.items` 为空数组。空输入、缺少 `aff` 参数的链接、无效前缀值、超过字段长度上限的输入会返回参数错误。

自动查询跨字段命中多个不同用户时返回 `code: "affiliate_lookup_ambiguous"`。此时使用上述前缀即可精确指定目标用户。
